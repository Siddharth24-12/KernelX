## Phase 6B — Algorithm Comparison

The comparison workspace executes 2–12 unique scheduler configurations against the same copied `WorkloadDefinition` snapshot. For every configuration, `ComparisonService` constructs fresh `SchedulingProcess` inputs and obtains a new `SchedulingService`; the existing Java `schedule(...)` implementation remains the only source of scheduling behavior. The service does not inject or call `SimulationRuntimeService`, `SimulationEngine`, `ProcessManager`, or `MemoryManager`, so a comparison cannot advance ticks, mutate live PCBs/memory/events, or add live DSA traces. A failed run aborts before `comparisons.json` is appended.

Results persist the workload snapshot and exact run configuration alongside the backend Gantt and `ProcessMetrics`. CPU utilization is calculated as non-idle Gantt duration divided by total elapsed schedule time; throughput is process count divided by that same elapsed time. Both use the scheduler's integer time model and include leading idle time in the denominator. A nonpositive total time is treated as a failed run. Waiting, turnaround, and response winners minimize; utilization and throughput maximize. Exact equal values remain a tie, and the UI does not claim a universally best algorithm.

Comparison reports use `JsonFileRepository<ComparisonReport>` and `comparisons.json`, with the repository's synchronized temporary-file and atomic replacement behavior. API: `POST /api/comparisons`, `GET /api/comparisons`, `GET /api/comparisons/{id}`, and `DELETE /api/comparisons/{id}`. The Algorithm Comparison page is routed at `/comparison`; its workload and report history calls use typed Axios modules. Backend integration tests use a temporary JSON directory and cover all five scheduling modes, RR quantum variants, deterministic output, metrics/ties, idle Gantt, persistence CRUD, invalid input, failure isolation, and preservation of active runtime/workload data.

## Phase 6C — System Analytics Observatory

`GET /api/analytics/snapshot` combines the active simulator's state, memory blocks, process PCB metrics, the actual backend schedule and tick telemetry in one synchronized runtime snapshot. `SimulationAnalyticsHistory` is shared by the runtime engine and analytics service. The engine emits exactly one sample after each actual tick, with the PID that executed that interval (null for idle), resulting simulation time, ready/waiting/completed counts and cumulative busy/idle ticks. Utilization is cumulative busy ticks divided by total observed ticks. No sample is generated by polling, reads, or unexecuted schedule plans. Sampling is one point per simulated tick; a 4,096-entry ring keeps the latest samples across resets and is cleared by backend restart.

Memory metrics are projections over `MemoryManager.snapshot()`. Allocation failures that occur because no contiguous free block can satisfy a request now emit a persisted `MEMORY_ALLOCATION_FAILED` event, while the existing API still returns its conflict response. External fragmentation is `100 × (1 − largestFreeBlock / freeMemory)`, or zero when `freeMemory` is zero. It is not a substitute for free capacity.

Process counts and per-process metrics are current PCB snapshots; historical creation, state change, termination, allocation and other events are from persistent `event_logs.json`. Event DTOs have event IDs and simulation time, but no wall clock or run ID. Therefore the analytics UI orders lifecycle rows by event ID and aggregates frequency at equal simulation ticks, including repeats after resets. Reset itself is not expanded into fabricated per-process transitions. Historical performance filters `ComparisonReport` records from `comparisons.json`; those remain separate from live CPU observations.

The responsive `/analytics` workspace refreshes live analytics every 3.5 seconds and loads persisted events and saved comparisons on entry/manual refresh. All reads are diagnostic and do not call instrumented DSA operations. Recharts present CPU utilization history, memory blocks, process state counts, event frequency/type distributions and filtered historical metric series; observed Gantt intervals come from actual tick samples, while scheduled/completed schedule data and per-process metrics come from the backend. ## Phase 6D — Interactive OS Experimentation Lab

`ExperimentService` accepts a saved workload ID, copies the workload into the report, and runs the baseline plus configured variants without calling `SimulationRuntimeService`. Scheduling variants use a new `SchedulingService` for each baseline/variant and copy all process rows before applying only the requested per-PID arrival, burst or priority overrides. Round Robin requires a quantum in 1–100000; preemption is valid only for Priority. A variant must differ from the baseline and all sibling variants must have distinct parameter combinations. The existing scheduler supplies every Gantt interval and process metric.

Memory experiments use the workload snapshot's fixed total memory and require First Fit as baseline plus both Best Fit and Worst Fit variants. One validated ordered request list (up to 512 operations) is replayed in full in each new `MemoryManager`; allocation failures count per strategy, while a later deallocation for a PID that did not get allocated is recorded as a no-op. Memory operation event managers and scheduler trace recorders are isolated and are never connected to live event persistence or DSA diagnostics. External fragmentation is `100 × (1 − largestFreeBlock / freeMemory)` when free memory is positive and zero otherwise. Allocation count/failure, capacity, largest block and fragmentation are compared; scheduler metrics use the same definitions as Phase 6B. Signed change is `variant − baseline`; absolute difference is its magnitude; percent change is omitted when the baseline value is zero.

`POST /api/experiments` executes and persists one complete experiment; `GET /api/experiments`, `GET /api/experiments/{id}`, and `DELETE /api/experiments/{id}` manage completed reports in separate atomic JSON storage (`experiments.json`). No report is appended if validation, baseline, variant execution or result construction fails. The `/experiments` page provides scheduling parameter editors, process overrides, ordered memory requests, report history and baseline comparisons. Backend tests use temporary JSON storage and verify deterministic results, allocation strategy replay, failure isolation, saved-workload immutability, unchanged active simulation state, events and DSA trace lists. Phase 6D verification baseline: `mvn test` — **64 passed, 0 failed, 0 errors, 0 skipped**; `npm test` — **55 passed** across 13 files; `npm run typecheck`, `npm run build`, and root `git diff --check` passed.

## Phase 3 implementation

### JSON persistence

- `backend/data/simulations.json`: completed-run snapshots containing schedule options, Gantt segments, process snapshots/metrics, memory state, and event history.
- `backend/data/configurations.json`: named algorithm, quantum, priority-mode, memory, and speed settings.
- `backend/data/event_logs.json`: structured persistent `SystemEvent` records.
- `backend/data/comparisons.json`: completed Phase 6B reports with immutable workload snapshots and backend schedule results.
- `backend/data/experiments.json`: completed Phase 6D scheduling and memory experiment reports.
- Separate archive/configuration/event services use `JsonFileRepository<T>`; records are persistence DTOs and do not capture custom DSA internals.
- Missing files/directories are created. Invalid JSON or wrong-root/null records are quarantined as `.corrupt-<uuid>.json`, then the active file is initialized to an empty array. Original corrupted bytes remain available.
- Writes are synchronized per repository, written to a unique same-directory temporary file, flushed, then replaced atomically where supported (replacement move is the fallback).
- API tests and JSON repository tests use isolated temporary directories. Tests do not read or overwrite the real backend data files.

### REST and runtime safety

- Process, simulation, scheduling, memory, event, archive, and configuration controllers expose the routes documented in `API.md`.
- Workload CRUD uses the shared atomic JSON repository; templates are generated and never persisted. Workload execution delegates to the existing synchronized runtime and does not introduce another scheduler.
- `SimulationRuntimeService` is the singleton API boundary for one session. Its synchronized methods serialize process mutations, ticks, and snapshots. Process and memory edits are rejected while a run is active/paused so the start-time scheduling plan remains consistent.
- `@RestControllerAdvice` returns one error DTO and maps invalid input to 400, missing resources to 404, invalid lifecycle/resource conflicts to 409, and storage/unexpected failures to a generic 500 response without stack traces.
- Central CORS policy allows the future Vite origin `http://localhost:5173`.
- `server.port` defaults to 8083 and can be changed with `SERVER_PORT`.

## Architecture

```text
REST controllers
  ├── SimulationRuntimeService (single synchronized in-memory session)
  │   ├── ProcessManager → Custom LinkedList + HashTable + ProcessTree
  │   ├── SimulationEngine → SchedulingService → Custom Queue / MaxHeap
  │   └── MemoryManager + EventManager
  ├── SimulationArchiveService → simulations.json
  ├── ConfigurationStoreService → configurations.json
  └── EventLogPersistenceService → event_logs.json

GlobalExceptionHandler + centralized CORS
```

The simulation engine remains independent of Spring. The REST layer reads DTO snapshots and does not serialize live linked lists, queues, heaps, hash buckets, or tree nodes. The frontend uses typed Axios endpoint modules and reads these real snapshots; scheduling and memory allocation remain server-owned.

## Known limits

- One in-memory simulation session per application process. Synchronization protects that process; multiple replicas must not share JSON files.
- A run’s schedule is computed at start; process mutations are locked while running/paused. Reset before changing the process set or priorities.
- Ticks are explicitly driven. Speed is metadata for a future polling UI, not a background timer.
- Memory allocations are explicit. Failed allocation reports 409 and does not automatically queue/retry the process.
- No simulation REST authentication, database, distributed locking, or saved-simulation restore route is included. Saved configurations are loaded into the scheduler frontend and submitted through the existing start route.

## Phase 8.5 — Cinematic hardware landing

The current `/` route uses a lazily loaded React Three Fiber scene; no raster artwork is used as the environment or as a texture. The board is a layered physical assembly with a beveled semiconductor package, four execution tiles, raised gold trace geometry, instanced edge contacts and mounting hardware. The linked list, max heap, hash buckets, FIFO buffer, process tree and allocation banks are spatial assemblies mounted on that board. Catmull-Rom paths become thick TubeGeometry glass shells, inner metal filaments and collar fittings; small capsule meshes follow pre-sampled points on those 3D curves.

Six camera waypoints and matching look targets are smoothly interpolated from scroll progress. Pointer position adds a small bounded target offset. The WebGL canvas is capped at 1.5 device pixel ratio, reduced to 1 on compact/reduced-motion devices, paused while hidden, and uses one shadow-casting key light with no post-processing. Reduced-motion mode switches to demand rendering and updates from scroll/pointer input. A static system map is the WebGL fallback. All animation is illustrative; the landing makes no simulator/API calls. Run the frontend from `frontend/` with `npm run dev -- --host 127.0.0.1 --port 5174`; the backend remains on its configured port (8083 by default). Verification and any remaining visual limitations are recorded in `PHASE8_5_REPORT.md`.
