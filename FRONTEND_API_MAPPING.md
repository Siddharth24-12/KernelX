# KernelX frontend ↔ backend API mapping

Base URL comes from `VITE_API_BASE_URL` (default `http://localhost:8083`). The frontend types mirror the Spring DTOs and the app sends requests through the shared Axios client.

## Data and runtime notes

- `frontend/src/api/` owns HTTP calls; components do not issue Axios requests directly.
- The shell polls process, memory, simulation and event reads every 3.5 seconds. Calls are grouped, do not overlap, stop on unmount, and set the connection state only from successful API reads.
- A simulation plan is calculated by Spring. The frontend only renders the returned Gantt and metrics. The memory allocator also remains exclusively in Spring.
- Phase 3 supports one active runtime session. Process and memory changes are disabled by the UI during `RUNNING`/`PAUSED`; backend errors remain authoritative.
- Browser-local scheduler defaults use the `kernelx.defaultSchedulerConfig` local-storage key. A loaded archive configuration uses `kernelx.pendingSchedulerConfig` until Scheduler reads and consumes it.
- The backend exposes no API to restore a saved simulation snapshot into the active runtime. The Archive page retrieves and displays saved simulation data without claiming it resumes the run.
- Navigation includes working routes for all application pages, including Workload Studio. Existing pages and DSA/algorithm behavior remain unchanged.


CPU Internals uses an interactive Three.js processor die with functional PDU, PMU, ALU, FPB and PTU units. Orbit, zoom, pan, focus and reset are client camera controls. DSA replay views use only backend snapshots and traces and are read-only. The PTU displays actual first-child/next-sibling links and explicitly keeps its final tree view static while replaying per-operation pointer events because per-step whole-tree snapshots are not recorded.

## Phase 6E integration notes

Saved workload load/execute endpoints revalidate persisted process and scheduler fields before touching the live runtime. Invalid stored definitions return a conflict response rather than partially loading a process set. Integration tests exercise these paths with temporary JSON data. The CPU Internals route defers loading the Three.js die until that scene is requested; playback data continues to come from the read-only backend snapshot and trace APIs. The automated frontend suite and production build do not substitute for manual WebGL/browser demo verification.
